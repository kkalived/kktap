# 项目说明文档

## 1. 项目简介

Tapp 是一款运行在 Windows 桌面上的电子便利贴软件，定位是“轻量、常驻、低打扰”的个人工作记录工具。

它既保留了传统便利贴的使用直觉，也加入了适合现代桌面工作流的能力：

- 多张便利贴自由摆放
- 便利贴堆叠、翻页和收起/分散
- 文本、图片、截图混合记录
- 待办清单式交互
- 历史记录恢复
- 基于 DeepSeek 的日报生成

项目当前主要面向 Windows 11 使用场景，强调安装简单、上手直接、数据本地保存。

---

## 2. 项目目标

本项目希望解决两个核心问题：

1. 让用户能像使用真实便利贴一样，快速记录碎片信息。
2. 让这些碎片记录进一步服务于工作流，例如截图归档、待办管理、日报生成。

因此，Tapp 不是单纯的记事工具，而是一个围绕“桌面即时记录”延展的小型效率工具。

---

## 3. 核心功能

### 3.1 便利贴基础能力

- 在桌面创建多张便利贴
- 自由拖动位置
- 自由调整大小
- 自动保存内容、位置、尺寸
- 关闭软件后再次打开可恢复上次状态

### 3.2 堆叠与翻页

- 多张便利贴可以叠放成一个堆
- 支持点击翻页查看堆中的其他便利贴
- 支持“收起”将散开的便利贴合并为一个整体
- 支持“分散”将堆叠后的便利贴重新拆开

### 3.3 文本与图片记录

- 支持直接输入文字
- 支持插入本地图片
- 支持截图后插入图片
- 支持图片在便利贴中缩放与自适应显示

### 3.4 待办清单

- 支持插入复选框式待办项
- 复选框可点击切换完成状态
- 完成后自动置灰并加删除线
- 支持连续换行生成下一条待办
- 支持删除复选框并还原为普通文本

### 3.5 截图能力

- 支持全局快捷键截图
- 支持框选区域截图
- 支持将截图插入便利贴
- 支持截图复制到剪贴板

### 3.6 历史记录

- 删除的便利贴进入历史记录
- 生成的日报也进入历史记录
- 历史记录支持分栏查看：
  - 日报
  - 便利贴
- 支持恢复与永久删除

### 3.7 AI 日报

- 支持从当天便利贴内容中生成日报
- 使用用户填写的“工作内容”作为轻量 RAG 上下文
- 自动过滤非工作信息
- 通过 DeepSeek API 生成工作日报
- 日报会生成新便利贴，并保存到日报历史中

## 4. 技术路线

项目当前采用的技术路线是：

`Electron 桌面应用 + 主进程集中管理 + 渲染进程原生前端 + 本地 JSON 存储 + DeepSeek API 日报生成`

### 4.1 Electron 作为桌面壳

选择 Electron 的原因是它天然适合这类桌面工具场景：

- 需要桌面窗口能力
- 需要系统托盘
- 需要全局快捷键
- 需要截图窗口覆盖层
- 需要打包成 Windows `.exe`

入口文件位于：

- [main.js](./tech-spec.md)

### 4.2 主进程集中负责系统级能力

主进程负责所有与系统资源和应用状态强相关的能力：

- 窗口创建与销毁
- 数据持久化
- 全局快捷键
- 托盘
- 截图服务
- DeepSeek 日报调用

这种设计能让渲染进程保持轻量，避免 UI 层直接操作文件系统和系统资源。

### 4.3 渲染进程使用原生 HTML/CSS/JS

项目没有引入 React、Vue 等前端框架，而是使用原生 HTML/CSS/JS。

这样做的考虑是：

- 项目体量较小
- 交互复杂度中等，但窗口较多
- 减少构建链复杂度
- 更方便直接控制 Electron 窗口型 UI

### 4.4 IPC 作为唯一进程通信方式

主进程和渲染进程之间全部通过 `contextBridge + ipcRenderer.invoke + ipcMain.handle` 通信。

这条路线保证了：

- 渲染进程不直接访问 Node.js API
- 安全边界清晰
- 后续模块扩展更稳定

桥接入口在：

- [preload.js](./tech-spec.md)

### 4.5 本地 JSON 持久化

项目不依赖数据库，当前采用本地 JSON 持久化。

主要优点：

- 结构简单
- 易于调试和迁移
- 适合个人桌面应用
- 便于做备份与容错恢复

当前本地保存内容包括：

- 便利贴堆栈数据
- 删除记录
- 日报历史
- 设置项

### 4.6 DeepSeek 日报生成

日报功能走的是“轻量 RAG + 大模型总结”的路线，而不是完整向量数据库方案。

当前流程：

1. 读取当天更新过的便利贴
2. 清洗 HTML、待办项和格式化内容
3. 读取用户填写的“工作内容”
4. 将“工作内容”作为轻量 RAG 上下文发送给 DeepSeek
5. 过滤非工作信息
6. 生成日报
7. 保存为新便利贴并写入日报历史

这样做的优点是：

- 实现成本低
- 用户理解成本低
- 已能覆盖日报生成的主要需求
- 后续仍可平滑升级到真正的向量检索 RAG

## 5. 当前架构拆分

### 5.1 主进程模块

- `noteStore.js`
  - 数据唯一真相源
  - 负责 JSON 读写、设置、删除记录、日报历史
- `windowManager.js`
  - 负责便利贴窗口创建、堆叠、恢复、层级控制
- `screenshotService.js`
  - 负责截图流程、裁剪、插入和剪贴板
- `hotkeyManager.js`
  - 负责全局快捷键注册与更新
- `trayManager.js`
  - 负责系统托盘
- `reportService.js`
  - 负责日报文本整理、DeepSeek 调用、日报生成
- `preload.js`
  - 负责向渲染进程暴露安全 API

### 5.2 渲染进程模块

- `note-stack/`
  - 便利贴主窗口
  - 包含文本编辑、图片、待办、底栏工具、翻页等
- `settings/`
  - 设置窗口
  - 包含快捷键、开机自启、DeepSeek 配置、工作内容
- `history/`
  - 历史记录窗口
  - 支持日报 / 便利贴 分栏显示
- `screenshot-overlay/`
  - 截图覆盖层

## 6. 数据设计思路

当前核心数据对象有四类：

### 6.1 Stack

表示屏幕上的一个便利贴堆。

包含：

- 位置
- 尺寸
- 旋转角度
- 是否收起
- 堆内便利贴数组

### 6.2 Note

表示单张便利贴内容。

包含：

- 文本内容
- 图片引用
- 字号信息
- 创建/更新时间

### 6.3 DeletedNote

表示已删除但可恢复的便利贴记录。

### 6.4 ReportHistory

表示已生成的日报历史。

包含：

- 日报标题
- HTML 内容
- 原始纯文本
- 创建时间

## 7. AI 日报设计说明

### 7.1 为什么不直接做完整 RAG

对于当前项目来说，完整 RAG 通常意味着：

- 文档切片
- 向量化
- 向量数据库
- 检索排序
- 上下文拼装

这套能力对于“根据当天便利贴生成日报”来说偏重了。

当前更合适的方案是：

- 用户填写一段明确的工作内容
- 这段文本作为轻量 RAG 上下文
- 模型根据它判断哪些便利贴与工作相关

这能解决当前 80% 的需求，同时保持实现简单。

### 7.2 后续可扩展方向

如果后续需要增强 AI 能力，可以沿这条路线继续升级：

1. 增加项目知识库目录
2. 自动读取本地工作文档
3. 做文本切片和向量化
4. 引入真正的检索层
5. 在日报生成前做检索增强

这时再升级为完整 RAG 会更合适。

## 8. 当前实现特点

### 优点

- 架构简单清晰
- 适合快速迭代
- 本地优先，数据可控
- 功能集中，桌面场景适配好
- 具备继续扩展 AI 能力的基础

### 当前限制

- 数据层仍是 JSON，不适合超大规模记录
- 富文本编辑基于 `contenteditable`，复杂格式仍需继续约束
- 日报功能目前属于轻量 RAG，不是真正知识库检索
- 历史记录和 AI 流程还可以继续做更强的预览与确认机制

- 从“便利贴工具”发展成“桌面轻工作流助手”
- 支持日报、周报、知识沉淀、任务追踪的一体化演进
